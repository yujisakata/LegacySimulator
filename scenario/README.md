# シナリオ管理

このディレクトリは、V1からV10までのシステム変更を「変更イベント」として管理する。
イベントは、意図的に複雑な実装を作るための命令ではない。業務要求と当時の制約から局所的には合理的な判断が行われ、その判断が実装、文書、テスト、運用、組織知に異なる形で反映される過程を記録するためのものである。

## ファイル

- `event_catalog.yml`: 再利用可能なイベントの型
- `version_timeline.yml`: V1〜V10に標準で適用するイベントと因果関係
- `examples/custom_event.yml`: 任意のVersionへ追加できるイベントの記述例

## イベントの基本構造

各イベントは、次の順序で解釈する。

```text
業務・制度・運用上のトリガー
  → 納期、予算、技術、組織上の制約
  → 当時の意思決定と却下案
  → 成果物ごとの反映状態
  → 暗黙知と将来の変更コスト
```

最低限、次の項目を持たせる。

| 項目 | 意味 |
|---|---|
| `event_id` | 履歴上で一意となるID |
| `catalog_ref` | `event_catalog.yml`にあるイベント型 |
| `trigger` | 変更の発端となった要求または出来事 |
| `constraints` | 納期、予算、人員、互換性などの制約 |
| `decision` | 実際に採用した対応と判断理由 |
| `artifact_updates` | 要件、設計、実装、テスト、運用資料の更新状態 |
| `knowledge_effect` | 形式知、暗黙知、散逸リスクへの影響 |
| `mdi_effect` | MDIの5次元に与える相対的な増減 |

## 運用規則

1. 過去Versionの成果物を後から全面改訂しない。訂正が必要な場合も、新しいVersionの差分または訂正記録として追加する。
2. `unchanged`は更新忘れとは限らない。期限、再試験範囲、管轄分離など、更新しなかった理由を記録する。
3. 実装変更には、対応する業務要求か運用上の理由を必ず持たせる。
4. 1つのVersionへ複数イベントを適用できる。`depends_on`で前後関係を示す。
5. イベントを別Versionへ移動するときは、技術プロファイルとナレッジ状態への影響も同時に再評価する。
6. `mdi_effect`は絶対評価ではなく、そのVersion内での相対的な変化量として扱う。
