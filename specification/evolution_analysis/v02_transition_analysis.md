# V1→V2分析 — 特約追加と互換維持

## 1. 一文で表す変化

V2は、既存の終身保険と下流処理を維持したまま二つの特約を6か月で発売するため、固定長レコードの未使用領域と既存COBOLへ局所的に項目・分岐を追加したVersionである。

## 2. 関係者と力点の変化

V1では新契約・査定部門が業務フローを主導した。V2では商品担当者の比重が高まり、災害死亡特約と入院特約の販売日が変更を駆動する。一方、契約受付、査定、証券発行の業務責任は既存部門に残る。

| 関係者 | 保持する知識 |
|---|---|
| 商品担当者 | 特約コード、保障額、組合せ条件、発売順序 |
| 初期設計者 | V1の設計意図と固定長配置 |
| COBOL主任 | 変更段落、空白・ゼロの互換条件 |
| 証券発行担当 | 下流帳票が参照する位置と変更可能範囲 |

「変更を求める人」と「業務・データを維持する人」が分かれ始める。

## 3. 当時の合理的判断

全面的なレコード再設計は、証券発行バッチ、帳票、運用手順の同時変更を必要とする。そのため、既存位置を変更せず、未使用領域へ特約コードを配置した。

```text
既存120文字を維持
  ＋
予約領域へAD・HIを追加
  ＋
既存査定へIF/EVALUATEを追加
```

この判断は、リリース対象と回帰範囲を限定し、別部署との同時調整を減らす点で合理的だった。

## 4. 事務運用がコードへ入った例

正式要件では空白が「特約なし」を表す。一部端末は英数字項目をゼロ初期化するため、実装では空白と`00`をともに特約なしとして受理する。

```text
商品上の意味: 特約なし
入力表現: 空白 または 00
実装判断: 両方を受理
```

これは単なる表記揺れではない。端末初期化と事務入力を吸収する互換ルールである。後世の開発者が要件書だけを正として空白のみ許可すると、既存入力経路との相違が発生する。

## 5. 複雑さが移った場所

- 主契約と特約の組合せ試験が必要になった。
- 予約領域が実質的な業務項目になった。
- 下流ジョブが予約領域を本当に無視しているか確認対象になった。
- 原本とV2差分を併読する必要が生じた。
- 商品コードの順序と販売計画の関係が担当者知識として残った。

V2のプログラム単体は拡張に成功したが、データレイアウトの「未使用」という意味は組織全体では不確実になった。

## 6. 文書と知識の変化

業務ルールと変更箇所は文書化された。一方、空白と`00`の互換条件、未使用領域を選んだ経緯、全下流ジョブの確認範囲は暗黙または未確認として残る。

知識接続度は100から91、MDIは10から13となる。増分はコード量だけではなく、下流確認と組合せ検証の追加による。

## 7. 若い開発者が誤読しやすい点

- 予約領域を安全に再利用できる空き領域と断定する。
- `00`受理を不正確な入力許容とだけみなす。
- 特約IFを共通化すれば作業が完了すると考える。
- 商品担当者の要求と、証券・新契約部門の運用責任を同一視する。

## 8. 次Versionへ持ち越したもの

固定長互換、差分文書、主契約と特約の組合せ、下流確認範囲の不確実性をV3へ持ち越した。V3ではさらに商品そのものを追加するため、既存プログラムへ追加するか、コピーするかという選択が発生する。
