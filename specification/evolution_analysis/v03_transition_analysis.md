# V2→V3分析 — 商品別コピーと差分文書

## 1. 一文で表す変化

V3は、医療保険・がん保険を3か月で発売し、既存商品の全面回帰を避けるため、終身保険の共通事務・査定処理を商品別COBOLへ複製したVersionである。

## 2. 開発関係者の変化

商品部が変更を主導し、開発者は複数案件を兼務する。商品追加チームには原本設計書の本文編集権限がなく、システム企画部の審査を期限内に完了できない。

V2までの初期設計者は主要な知識保持者から外れ、COBOL主任と医療保険商品担当者が中心になる。商品固有知識は増えるが、V1から継承した共通業務の判断理由を説明できる人は減る。

## 3. 当時の合理的判断

検討された選択肢は次のとおりである。

| 案 | 採否理由 |
|---|---|
| 全商品共通査定へ再構成 | 設計承認と全面回帰を3か月で完了できない |
| V2へMI・CI分岐を直接追加 | 既存商品への変更・試験範囲が広い |
| 可変長商品属性を新設 | 下流と共通ファイルの同時改訂が必要 |
| 商品別COBOLへ複製 | 既存商品の変更を限定できるため採用 |

このコピーは設計能力の不足ではなく、納期、承認権限、回帰可能範囲に対する局所最適だった。

## 4. V3はV2の置換ではない

```text
NBENTRY / NBASSESS
  終身保険＋AD・HI

MDENTRY / MDASSESS
  医療保険MI＋がん保険CI
```

V3はV2の後継プログラムではなく、隣に増えた商品系統である。V3単体の行数が少なくても、全体ではV2系とV3系を両方維持する。

## 5. 同じ位置が違う意味を持つ

固定長61～68桁は、商品コードと組み合わせて解釈される。

| 商品 | 61～68桁の意味 |
|---|---|
| WL | 死亡保険金額 |
| MI | 入院給付日額 |
| CI | がん診断給付金 |

さらに、V2で75～94桁にあった特約項目は、V3では75～120桁を空白とする。同じ120文字でも同じスキーマではない。

## 6. コード類似度が示すもの

V2とV3の査定処理には大量の共通行がある。類似度が高いことは共通化候補の証拠になるが、即時の統合判断にはならない。

分類すべき対象は三つある。

1. 本当に共通する新契約事務ルール。
2. コピーされた技術処理。
3. 見た目は同じでも商品ごとに変更責任が異なる処理。

AIが文字列類似だけで統合すると、商品別リリース、決裁条件、保障額意味の差を見落とす可能性がある。

## 7. 文書が別冊化した理由

原本設計の変更審査が間に合わず、商品追加チームに編集権限もないため、V3は差分別冊を発行した。これは承認証跡を期限内に確保する合理的な方法だった。

一方、正しい理解にはV1原本、V2追補、V3変更要求、V3商品差分、V3設計別冊を順に読む必要がある。仕様の正しさが一冊の中ではなく、読順によって成立する。

## 8. 次Versionへ持ち越したもの

- 共通ルールが複数商品プログラムへ複製された。
- 原本と差分別冊の優先順位が必要になった。
- 共通ルール変更時に修正すべき全プログラムが未確認になった。
- 商品ごとのデータ意味と配布単位が分かれた。

知識接続度は91から78、MDIは13から18となる。V4では、この商品軸へ制度適用日の時間軸が加わる。
