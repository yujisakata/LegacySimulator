# V8→V9分析 — 横断監査とSpring世代併存

## 1. 一文で表す変化

V9は、旧Spring、Spring Boot、COBOL、外部連携を通過する全査定判断へ監査証跡を追加しながら、新しい本人確認連携だけを独立したSpring Bootアプリとして短期リリースしたVersionである。

## 2. 監査は既存機能の外側ではない

監査要件は、入力、判定理由、操作者、発生時刻、取引キーを全査定判断について記録することである。既存処理を一度に再構成できないため、各世代へ個別ログを追加し、夜間に監査DBへ集約する。

```text
旧Springログ ─────┐
Spring Bootログ ──┼→ 夜間集約 → 監査DB
COBOL結果・ログ ──┘
```

この判断は監査開始日までに対象を網羅し、既存責務を維持する点で合理的である。一方、監査上の一取引を再現するには、三世代のログを結び付ける必要がある。

## 3. 「同じ取引」の識別が難しくなる

各システムは異なるキーを使い得る。

- Spring受付番号。
- 外部取引ID。
- 再送キュー番号。
- COBOL申込番号。
- 監査イベントID。
- 本人確認アダプタのメッセージID。

監査DBでは取引キーへ正規化するが、その変換規則自体が重要な業務・技術知識になる。キー変換を誤ると、別案件を同一履歴に見せる、または一案件を複数履歴に見せる可能性がある。

## 4. 時刻は事実ではなく解釈対象になる

旧Spring、Spring Boot、COBOL、外部先でタイムゾーン、時計精度、記録タイミングが異なる。そのためUTCへ正規化し、元時刻とオフセットも保存する。

```text
元時刻 + オフセット
        ↓
     UTC時刻
```

ただし、UTCが同じでもログ出力の意味は同じとは限らない。

- 受付開始時刻か完了時刻か。
- DBコミット前か後か。
- メッセージ送信要求時か送達確認時か。
- COBOLジョブの入力時か結果出力時か。

監査順序を理解するには、時刻変換だけでなく、各ログがどの業務イベントを表すかを復元する必要がある。

## 5. 新しいSpring Bootは独立して見えても完全独立ではない

本人確認アダプタは、既存Springモノリスのビルド周期に合わせられないためSpring Bootへ分離する。外部先のリリース周期へ合わせられる合理的な判断である。

一方、共有DBを維持し、DB更新後にメッセージを発行する順序を契約として残す。

```text
Spring Boot
  1. 共有DB更新
  2. メッセージ発行
  3. 旧Spring・後続処理が参照
```

デプロイ単位は独立しても、データと順序では旧モノリスに結合している。これはマイクロサービスかモノリスかという名称だけでは評価できない。

## 6. 監査DBは業務正本とは限らない

監査DBは「各システムが何を記録したか」の集約である。最終査定の業務正本、契約原簿、外部本人確認結果と常に同じ意味になるとは限らない。

例えば次があり得る。

- ログ出力後にDB更新が失敗する。
- DB更新後にメッセージ送信が保留される。
- 再送前後で複数ログが生じる。
- COBOL結果理由がJava側の事前判定理由と異なる。
- 手動補正が元ログとは別経路で記録される。

監査データが豊富になるほど、ログがあることと業務結果が正しいことを区別する必要がある。

## 7. 切戻しも多世代になる

Spring Bootだけを以前の状態へ戻しても、すでに共有DBを更新し、未送信または送信済みメッセージが残る場合がある。旧モノリス、共有DB、メッセージ、外部先をどの順序で扱うかが切戻し手順になる。

この順序はコードだけでは完結せず、運用資料と実行履歴が必要である。

## 8. 複雑さの増加

MDIは110から150、知識接続度は27から21となる。

- 監査要件が全世代へ横断追加された。
- 取引キーの対応表が必要になった。
- 元時刻、オフセット、UTC、イベント意味を区別する。
- Spring世代が複数になった。
- 共有DB更新とメッセージ発行の順序制約が加わった。
- 通常処理、再送、再集約、切戻しの冪等性を確認する。

## 9. 若い開発者が誤読しやすい点

- 監査DBを最新かつ唯一の業務履歴とみなす。
- UTC正規化だけで処理順序を確定できると考える。
- 同名の取引キーを同じ生成規則だとみなす。
- Spring Bootであるため旧Springから独立していると判断する。
- DB更新後のメッセージ発行を通常の実装順序とみなし、障害・再送時の契約を調べない。
- ログ追加は業務ロジックに影響しないと考える。

## 10. 次Versionへ持ち越したもの

V9は、V1からのCOBOLルール、商品別コピー、制度日時点、Java複製DB、Spring二重判定、チャネル権限、外部非同期処理、複数Spring世代、監査相関をすべてV10へ持ち越す。

この時点で、単一の資料、コードベース、DB、ログ、担当者のどれも、現行業務全体の正解を単独では表さない。
