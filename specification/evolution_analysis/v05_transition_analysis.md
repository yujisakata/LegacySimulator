# V4→V5分析 — 有識者異動とJava参照系

## 1. 一文で表す変化

V5は、V1～V4の判断背景を知る初期有識者が異動する時期に、COBOL契約原簿を更新の正本として維持しながら、前夜時点の複製データをJavaでWeb照会する新しい参照系を追加したVersionである。

## 2. 最も大きな事件は技術導入だけではない

初期設計者と査定システム主任が異動し、引継ぎ期間は2週間である。月次処理と障害対応を継続する必要があるため、引継ぎは次を優先する。

- 主要ジョブ。
- 再実行手順。
- 障害連絡先。
- 主要プログラム一覧。
- 固定長から照会DBへの変換規則。

これは日常運用を継続するために合理的である。一方、30日猶予、2,000万円境界、商品横断の重複段落、例外再起票、再告知補正の背景は優先順位が下がる。

知識は一度に消えるのではない。「今日の運用に必要な知識」と「将来の変更に必要な知識」の選別によって、後者が徐々に確認しにくくなる。

## 3. Java照会を別系統にした理由

支社は契約進捗をWebブラウザで確認したい。しかし、Javaから契約原簿を直接参照・更新すると、中核の性能、可用性、運用責任までJava側へ広がる。

そこで次の構成を採用した。

```text
COBOL契約原簿（更新の正本）
  ↓ 夜間固定長スナップショット
照会用RDB
  ↓ Servlet/JDBC
支社Web照会
```

利用者体験を改善しながらCOBOL査定へ直接変更を加えない点で合理的な判断である。

## 4. 「正本」が一つでも、見える事実は二つになる

正式な更新正本はCOBOL契約原簿である。一方、支社担当者が日中に見るのは前夜時点の照会DBである。

```text
業務上の最新状態  COBOL契約原簿
利用者が見た状態  Java照会DBの前夜スナップショット
```

画面に基準日を表示することで、この差を業務上許容する。したがって、前日状態は障害ではなく、合意された整合性モデルである。

後世の開発者が照会DBを最新の契約状態と解釈したり、基準日表示を不要な画面項目と判断したりすると、支社説明と実データの関係を誤る。

## 5. 空白・ゼロ・NULLの意味変換

固定長とRDBでは、未設定値の表現が異なる。

| COBOL側 | Java/DB側 | 意味 |
|---|---|---|
| 状態が空白 | NULL | 未設定 |
| 金額がゼロ | 数値0 | 実際のゼロ |
| 金額が空白 | NULL | 未入力・不明 |

空白金額をゼロへ変換すると、「値がない」と「ゼロである」が同一になる。この変換規則は技術的な型変換であると同時に、業務意味の翻訳である。

## 6. 組織と障害対応が二層化する

| 問い合わせ | 主担当 |
|---|---|
| Web画面が表示されない | Java運用担当 |
| 表示値が前日である | 基準日を確認し、通常運用か判定 |
| 原簿の内容が想定と異なる | COBOL保守担当 |
| 件数・文字変換が一致しない | Java・COBOL共同確認 |

一つの「契約状態の問い合わせ」が、画面、同期、変換、原簿のどの問題かによって担当をまたぐようになる。

## 7. 複雑さが移った場所

- 技術スタックがCOBOLとJava/Servlet/JDBCへ増えた。
- 同一契約に原簿表現と照会表現が生まれた。
- 夜間同期という時間境界が加わった。
- 空白、ゼロ、NULLの意味対応が必要になった。
- 障害の責任分界が画面、同期、原簿で分かれた。
- 初期設計理由を知る人が日常保守から外れた。

MDIは26から41、知識接続度は66から49となる。機能追加だけでなく、有識者異動と意味変換が確信度を大きく下げた。

## 8. 若い開発者が誤読しやすい点

- RDBをCOBOLより新しいため正本だと判断する。
- 前日状態を直ちに同期不良と判定する。
- NULL変換を単なる実装詳細とみなす。
- Javaから更新できない制約を技術的な不足とだけ評価する。
- 2週間の引継書に書かれていないことを、存在しない業務とみなす。

## 9. 次Versionへ持ち越したもの

V5は参照だけをJavaへ移した。V6では受付もSpringへ移るため、Java側が更新する受付DBと、COBOLが決定する最終査定が併存する。参照系の二層化は、業務処理の二重化へ進む。
