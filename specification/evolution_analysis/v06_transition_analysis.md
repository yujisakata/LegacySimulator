# V5→V6分析 — Spring受付とCOBOL査定

## 1. 一文で表す変化

V6は、Javaを参照専用から新契約受付へ広げ、利用者へ即時点検を提供しつつ、最終査定と契約原簿はCOBOLに残した段階移行のVersionである。

## 2. 利用者価値を先行した合理的判断

受付画面だけでなく必須、年齢、商品コードを即時点検したい。しかし、査定バッチまで同時にJava化すると、商品、制度日、決裁、旧契約再現を含む回帰量が期限に合わない。

そのため次を採用した。

```text
Spring受付・事前点検
  ↓ 80文字固定長
COBOL最終査定
  ↓
契約原簿・結果
```

顧客・事務担当者には早い入力応答を提供し、長年の査定実績を持つCOBOLは維持する。典型的で合理的な段階移行である。

## 3. 同じ業務ルールが二か所に存在する

年齢、商品、必須項目の一部はSpringとCOBOLの両方で判定される。

```text
Spring判定  入力時の利用者応答
COBOL判定   最終査定としての公式結果
```

見た目は同じ条件でも責任が異なる。Springは早期フィードバック、COBOLは最終判断を担当する。

この状態でルールを一方だけ変更すると、画面で受理した案件を夜間にCOBOLが拒否する、または画面で受理しない案件をCOBOLなら処理できる、という差が生じる。

## 4. 固定長ファイルが正式な境界になる

V6では80文字固定長が単なる古いデータ形式ではなく、別組織・別技術間の正式な契約になる。

- Springは受付番号、商品、年齢、金額を決められた位置へ出力する。
- COBOLはその位置と表現を正として査定する。
- 再送でも受付番号を変更しない。
- Java受付DBとCOBOL原簿を受付番号で相関する。

固定長をJSONへ変換するだけでは、番号維持、空白表現、再送、締め時刻の意味までは移行できない。

## 5. 月末性能対応が業務SLAを分岐させる

月末に夜間バッチ枠を超過したため、2,000万円以上の高額契約を後続ジョブへ分離した。

```text
2,000万円未満  NORMAL → 翌朝処理を優先
2,000万円以上  HIGH   → 後続ジョブ、結果反映は1営業日遅い
```

この判断は、全件を遅らせる代わりに通常案件を翌朝までに処理する運用最適化である。

同じ2,000万円という値が、V1では決裁権限、V6では処理レーン選択にも現れる。両者が同じ業務根拠か、既存境界を運用上再利用したのかは、コード上の数値一致だけでは確定できない。

## 6. 時間が三層になる

V6の契約には少なくとも次の時点がある。

1. Springで受付・事前点検された時点。
2. 夜間固定長が出力された時点。
3. COBOLで最終査定され、結果が反映された時点。

高額案件では3がさらに1営業日遅れる。画面状態、照会DB、COBOL原簿の値が異なる時間帯は、設計上存在する。

## 7. 組織境界

Java刷新チームとCOBOL保守チームは別組織である。

| 判断 | 主な責任 |
|---|---|
| 即時点検と画面応答 | Springチーム |
| 固定長生成 | Springチーム、COBOL側と共同確認 |
| 最終査定 | COBOLチーム |
| 夜間受渡し | 運用統括 |
| 現新差異 | 両チームと業務担当 |

仕様上は「COBOL優先」と書けても、利用者へ返したSpringの判定を後で訂正する運用まで設計しなければ業務は完結しない。

## 8. 複雑さの増加

MDIは41から63、知識接続度は49から42となる。

- 判定箇所が二重化した。
- Java RDBとCOBOL原簿の項目別正本が必要になった。
- 夜間境界と結果反映遅延が加わった。
- 再送時の同一性が業務要件になった。
- 性能対策が契約金額別SLAを生んだ。

## 9. 若い開発者が誤読しやすい点

- Spring側の検証を唯一の現行ルールとみなす。
- COBOL側の重複検証を不要と即断する。
- 固定長をデータ形式だけの問題とみなす。
- HIGH/NORMALを純粋な性能分類とみなし、顧客・事務への反映日差を見落とす。
- 受付番号の維持をID生成の実装詳細とみなし、再送・照合の業務キーであることを見落とす。

## 10. 次Versionへ持ち越したもの

SpringとCOBOLの責務境界、二重判定、夜間受渡し、高額レーン、再送同一性をV7へ持ち越す。V7ではさらに社員・代理店チャネルとベンダ交代が加わり、技術境界が契約上の組織境界と重なる。
