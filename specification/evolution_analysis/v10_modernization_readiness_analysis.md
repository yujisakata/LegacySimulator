# V9→V10分析 — なぜコード変換からモダナイズを始められないか

## 1. 結論

V10のシステムは技術的に変更不可能なのではない。しかし、現在の証拠だけで業務責任を持って一括変換することはできない。

理由は、COBOLが古いからでも、Springが複数世代だからでも、ドキュメントが差分化したからでもない。次の多様な事情が同時に存在し、それらの関係を一人も一つの成果物も完全には説明できないためである。

- 商品別に複製されたルール。
- 過去時点を再現する新旧制度ロジック。
- 支社担当者が入力する例外フラグ。
- COBOL原簿、照会DB、受付DB、共有DB、監査DBの役割差。
- SpringとCOBOLに二重実装された判定。
- 夜間境界と高額案件の遅延。
- 社員・代理店の権限と既定値。
- 外部先ごとの通信、再送、重複排除。
- 複数世代ログの取引キーと時刻補正。
- ベンダ契約、運用承認、障害時の共同調査。
- 変更理由を知る有識者の異動。

V10はモダナイズ完了版ではなく、モダナイズ可能性を回復するための調査・知識復元Versionである。

## 2. 「正解」が複数種類ある

V10で区別すべき正解は少なくとも次の五つである。

| 種類 | 例 |
|---|---|
| 業務上望ましい動作 | 現在の規程・商品方針に合う判定 |
| 現行実装の動作 | 現在COBOL、Spring、Bootが実際に行う判定 |
| 運用上成立している動作 | 手動フラグ、再送承認、件数確認を含む結果 |
| 過去時点を再現する動作 | 旧制度・旧契約の再査定 |
| 監査上説明できる動作 | 入力、理由、操作者、時刻、経路を追跡できること |

これらは常に一致するとは限らない。最新要件だけを正とすると現行互換性を失い、現行コードだけを正とすると現在不要な運用や過去の補正まで将来設計へ固定する可能性がある。

## 3. 単一のSource of Truthがないのではなく、項目ごとに正本が違う

「正本DBはどれか」という質問だけでは足りない。

| 情報 | 正本または主要証拠の候補 |
|---|---|
| 最終査定結果 | COBOL契約原簿・査定結果 |
| Web受付中状態 | Spring受付DB |
| 支社が見た契約進捗 | 基準日付き照会DB |
| 本人確認応答 | 外部応答・Spring Boot・連携状態DB |
| 再送承認 | 運用台帳・再送キュー |
| 監査経路 | 監査DBと各発生元ログ |
| 旧制度再現 | 旧COBOL段落、適用基準日、過去入力 |
| 商品ルールの意図 | 商品文書、差分設計、担当者レビュー |

データベースを統合する前に、項目単位・時点単位・用途単位で正本を決める必要がある。

## 4. 技術世代の数より境界の意味が問題になる

V10ではCOBOL、JCL、固定長、Servlet/JDBC、旧Spring、Spring Boot、SQL、SOAP、ESB、キュー、SFTP、メッセージ、監査ログが併存する。

技術の種類が多いこと自体は解決可能である。難しいのは、各境界が業務・組織上の契約になっていることだ。

```text
固定長境界   別チーム間の正式IF
夜間境界     査定・照会の業務時点
共有DB       独立リリース間の順序契約
再送キュー   運用承認と外部先契約
監査集約     説明責任と保存義務
```

境界を新技術へ置き換える場合、その境界が担っていた責任分担と統制を別の形で設計し直さなければならない。

## 5. コードの重複には複数の理由がある

V10の重複を一括して整理対象にしてはいけない。

| 重複の種類 | 例 | 判断に必要な情報 |
|---|---|---|
| 本当に共通な業務 | 日付形式、入力基本点検 | 全商品で同時変更してよいか |
| 商品別責任のためのコピー | NBASSESSとMDASSESS | 商品別発売・回帰・配布単位 |
| 利用者応答と最終査定の二重判定 | SpringとCOBOLの年齢・商品判定 | どちらを正とするか、差異時の業務 |
| 新旧制度の意図的併存 | OLD/NEW段落 | 過去再現の対象期間 |
| 接続先別翻訳 | SOAP/ESB/QUEUEアダプタ | 外部原典と共通形式の意味差 |
| 監査用再表現 | 各ログMapper | 原時刻、キー、理由の保存要件 |

文字列類似や静的解析は候補発見に有効だが、統合可否の承認までは行えない。

## 6. 時間が多層化している

V10の一件の申込には、少なくとも次の時間が関与する。

- 受付日。
- 告知日。
- 再告知日。
- 制度施行日。
- Spring受付時刻。
- 夜間締め時刻。
- COBOL査定日。
- 高額案件の後続処理日。
- 外部送信・応答時刻。
- 再送時刻。
- DB更新時刻。
- メッセージ発行時刻。
- ログ元時刻、オフセット、正規化UTC。
- 照会DB基準日。

現在値の移行だけでは、なぜその結果になったか、過去日時点でどう判定されたか、利用者が当時何を見たかを再現できない。

## 7. 人の作業が実装の一部である

現行機能には、次の人手作業が含まれる。

- 不備照会と期限管理。
- 再告知フラグの判断・入力。
- 再告知件数と適用日の確認。
- 夜間同期の件数・文字変換確認。
- JavaとCOBOLの受渡し確認。
- 手動再送の承認。
- 外部障害時の組織間連絡。
- 監査集約エラーの確認。
- 例外案件の査定・決裁。

画面、API、バッチだけを移しても、これらの判断入力、承認、照合、証跡を移さなければ業務能力は同等にならない。

## 8. 組織構造がアーキテクチャへ写されている

V1では業務部門と専任開発チームが同席していた。V10では、商品、査定、支社、運用、法務、監査、Javaベンダ、COBOLベンダ、外部接続先、刷新チームが、それぞれ一部分を担当する。

その結果、次の境界が技術構造へ残る。

- 商品別ロードモジュール。
- JavaとCOBOLの固定長IF。
- 別スケジューラ。
- 接続先別アダプタ。
- 共有DB。
- 監査集約。
- 運用台帳。

モダナイズで技術境界を変更すると、予算、契約、承認、当番、障害連絡、監査責任まで再設計対象になる。

## 9. 文書は不正確なのではなく、異なる時点と目的を記録している

V1原本、V2追補、V3商品別冊、V4制度追補、障害票、V5引継書、V6以降の追加要件、外部IF、監査運用は、それぞれ作成時点と目的が違う。

したがって、最新文書一冊だけを正解にできない。古い文書も過去再現や現行コードの由来を説明する証拠であり、運用資料はソースにない手順を説明する。

文書間の差は直ちに誤りを意味しない。時点差、対象商品差、責任範囲差、予定と本番補正の差を分類する必要がある。

## 10. テスト合格だけでは将来仕様を決められない

既存テストは、各Versionで必要だった代表ケースと局所回帰を記録する。現行動作の観測には重要だが、次を自動的には証明しない。

- 全商品、全制度日、全支社の組合せ。
- Spring事前点検とCOBOL最終査定の完全一致。
- 全外部先の同時障害と遅延応答。
- 再送と手動補正の競合。
- 共有DB更新後のメッセージ未送信。
- 監査ログと最終査定理由の一致。
- 現行動作が現在も望ましい業務動作であること。

ゴールデンテストは「現行がこう動く」という証拠であり、「将来も同じであるべき」という承認ではない。

## 11. V10開始時の数値が示すこと

| 指標 | V1 | V9 | V10開始時 | V10目標 |
|---|---:|---:|---:|---:|
| 機能数 | 10 | 30 | 32 | 変更対象に応じて管理 |
| MDI | 10 | 150 | 240 | 知識復元により変更5次元を低減 |
| 知識接続度 | 100 | 21 | 21 | 75 |

V10のMDI 240は、AIツール導入後の完成値ではない。V1～V9の資産と未解決知識をすべて引き受けた調査開始時点を表す。

知識接続度21はコード品質の点数ではない。業務、設計、実装、データ、テスト、運用を結ぶ関係のうち、組織が根拠付きで説明できる割合が低い状態を教材上表現している。

## 12. V10が採用する方法

V10は、単一成果物を正解にせず、知識エッジを復元する。

```text
要件 ─┐
設計 ─┼→ 対応候補 → 根拠・反証・確信度 → 開発レビュー → 業務レビュー
コード ┤
テスト ┤
ログ ─┤
運用 ─┘
```

確信度は教材上、要件0.2、設計0.2、コード0.3、テスト0.3で算出する。反証がある候補は最大0.5とし、要レビューにする。AIは候補抽出と差異検出を支援するが、業務判断の承認者にはしない。

## 13. 一括変換案が適さない理由

### COBOL・Javaの一律自動変換

構文と処理順は変換できても、30日の由来、旧制度保持期間、手入力フラグの責任、前日スナップショットの許容、再送承認までは決定できない。

### 最新文書を正とした再実装

本番補正、コードでのみ維持された互換条件、運用台帳、現行データ表現、過去再現条件を見落とす可能性がある。

### 現行コードをそのまま仕様化

現行動作は把握できるが、現在も必要な業務と、過去制約のため残った実装を区別できない。

### 新DB・APIへ先に統合

項目別正本、時間意味、NULL・空白・ゼロ、取引同一性、再送、監査順序を確定する前に統合すると、後から差異の理由を説明しにくい。

## 14. モダナイズ開始条件

V10で先に回復すべき条件は次のとおりである。

1. 重要業務ルールから、設計、コード、データ、テスト、運用への対応が根拠付きで追跡できる。
2. 各項目の正本と、正本が切り替わる時点を説明できる。
3. 商品別コピー、二重判定、新旧段落を、統合可能・責任差・過去再現へ分類できる。
4. 手動入力、承認、照合を含む業務フローを再現できる。
5. 代表的な過去時点と現行ケースをゴールデンデータで再現できる。
6. 反証と未確認事項を、未解決のまま可視化できる。
7. 現行動作と将来も維持すべき動作を業務担当が区別できる。
8. 技術切替と同時に変更される組織責任、運用、監査を定義できる。

この条件を満たして初めて、段階移行、機能置換、データ移行、共通化の順序を責任を持って選択できる。

## 15. 若いAIモダナイズ開発者への問い

コードを見つけたら、すぐに整理案を出す前に次を問う。

- この条件は、どの業務イベントから生まれたか。
- 誰の一日を成立させる処理か。
- どの時点の契約を判定しているか。
- 同じ値を別システムはどう表現するか。
- この処理の前後に、人の判断や承認がないか。
- 重複は偶然か、責任分離か、過去再現か。
- 使われていないように見える処理は、監査・再査定・切戻しに必要ではないか。
- テストは現行動作と将来要件のどちらを証明しているか。
- その説明に反証はないか。
- 分からないことを分からないまま管理できているか。

## 16. 最後に伝えるべきこと

V10の現行構造は、過去の開発者が一度に設計したものではない。

```text
紙・郵送・査定人員への最適化
  ＋ 特約の短期発売
  ＋ 商品別の承認・配布
  ＋ 法令施行日と過去再現
  ＋ 支社の例外事務
  ＋ 有識者異動
  ＋ Javaによる参照改善
  ＋ Springによる受付改善
  ＋ 夜間性能対策
  ＋ 代理店チャネル
  ＋ ベンダ契約境界
  ＋ 外部接続先の事情
  ＋ 再送と重複排除
  ＋ 監査期限
  ＋ Spring世代の独立リリース
```

各時点では、期限内に事業と運用を成立させる合理的な判断だった。その判断が、後のVersionでは前提条件になる。前提条件の理由を説明する知識だけが、コード、差分文書、ログ、運用、人へ分散していった。

したがってV10の中心課題は、古いコードを新しいコードへ変えることではない。

> なぜ存在するかを説明できないものを、残すべきか変えるべきか判断できる状態へ戻すこと。

これが、V10で最初に行うモダナイゼーションである。
